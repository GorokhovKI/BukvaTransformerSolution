# План: user-условная модель (user conditioning)

> Ветка-преемник `user-adaptation`. Документ описывает, ЧТО строим, ПОЧЕМУ будет выигрыш и что модель заменит/добавит/уберёт. Реализация — только после одобрения.

## 1. Идея

Добавить в модель явную обусловленность пользователем: `user_id → обучаемый эмбеддинг`,
который прибавляется к CLS-токену перед энкодером.

- `nn.Embedding(N_users + 1, HIDDEN_SIZE)`, индекс 0 = `<unk>` (обучаемый, «среднестатистический пользователь»).
- `ModelConfig.user_dim` (0 = обусловленность выключена → модель тождественна текущей, обратная совместимость чекпойнтов и ONNX).
- Словарь `user_id → idx` сохраняется в чекпойнт (`user_vocab`).

Модель обучается заново (~150 эпох, те же гиперпараметры) на всех 135 train-пользователях
и учится разделять «ЧТО показано» (буква) и «КТО показывает» (стиль пользователя).

## 2. Почему результат будет именно таким

**Почему выиграет там, где адаптер не выиграл:**

- Адаптер дообучался постфактум на 5 сэмплах одного пользователя — данных критически мало.
- User-условная модель обучает структуру «как пользователи различаются» совместно на данных
  ВСЕХ 135 пользователей (median 27 сэмплов/пользователя, min 4, max 46). Эмбеддинг известного
  пользователя — это сжатие его ~27 сэмплов в один вектор, выученное с полным градиентным
  сигналом всей задачи, а не дообученное в изоляции.
- База сейчас тратит ёмкость энкодера на межпользовательскую вариацию (форма кисти, манера,
  камера). Условность выносит этот фактор в явный вход — энкодеру остаётся только жест.

**Ожидаемый результат по сценариям:**

| Сценарий | Ожидание | Обоснование |
|---|---|---|
| **Известный пользователь** (135 train-пользователей, его held-out сэмплы) | **Измеримый прирост**, особенно у пользователей с низкой базовой точностью | персональный сдвиг выучен в train на его же данных |
| **Неизвестный пользователь** (официальный test, 20 пользователей) | Не хуже базы (91.21%) | `<unk>`-эмбеддинг = «средний пользователь»; критерий — отсутствие деградации |
| **Новый пользователь в demo** | `<unk>` + существующий адаптер (ортогональны, совместимы) | эмбеддинг не знает пользователя → работает накопление сэмплов как раньше |

Честная оговорка: «гарантированный выигрыш» относится к известным пользователям на held-out
данных. Если прирост < +1 п.п. — решение пересматриваем (см. §5, критерий 1).

## 3. Что добавит / заменит / уберёт

### Добавит
| Что | Куда |
|---|---|
| `ModelConfig.user_dim`, `nn.Embedding(N+1, HIDDEN_SIZE)` | `model.py` — прибавка к CLS перед энкодером; `forward(x, mask, user_idx=None)` |
| `user_vocab` в чекпойнте, маппинг `attachment_id → user_id → idx` | `train.py` — `SignDataset` отдаёт `user_idx`; сохранение словаря |
| `eval_user_conditioned.py` — три цифры: известные (held-out train-пользователей), официальный test с `<unk>`, пер-пользовательские дельты | новый скрипт |
| `--user` для известных пользователей → их эмбеддинг | `demo.py` (P4) |
| `PLAN_USER_CONDITIONED.md`, обновление `SPECIFICATION.md` после одобрения | документация |

### Заменит
- Для известных пользователей: user-эмбеддинг **заменяет** few-shot адаптер как основной механизм — персональный сдвиг уже выучен, дообучение не нужно.
- Основную eval-метрику: held-out train-пользователей; официальный test остаётся санитарной проверкой (нет деградации).

### Уберёт
- Ничего из базы не удаляется: `user_dim=0` → модель побайтово совместима с текущей (старый чекпойнт грузится, ONNX с baked `<unk>` работает как раньше).
- Адаптер (`personalization.py`) не удаляется — остаётся для неизвестных/новых пользователей.

## 4. Фазы реализации

- **P1 — модель и пайплайн**: `model.py` (эмбеддинг, обратная совместимость), `train.py`
  (user_idx из `annotations.tsv`, словарь в чекпойнте). Проверки: старый чекпойнт грузится
  при `user_dim=0`; оверфит-тест на одном батче; сплит без утечки пользователей
  (утверждение: test-пользователи не встречаются в train).
- **P2 — обучение**: полный прогон ~150 эпох, те же гиперпараметры и аугментации, отдельная
  директория результатов (например `results_usercond/`). Оценка времени — как у базового
  обучения (~часы на CPU).
- **P3 — измерение**: `eval_user_conditioned.py` — три цифры из §3 + пер-пользовательская
  таблица приростов (кто из слабых пользователей выиграл больше всех).
- **P4 — интеграция**: `demo.py --user` для известных пользователей; решение по ONNX/Unity
  (baked `<unk>` как константа, либо `user_idx` как второй вход — решить по потребностям Unity).
- **P5 — документация**: обновить `SPECIFICATION.md` (§3, §5, риски) после одобрения реализации.

## 5. Критерии приёмки

1. Известные пользователи: held-out точность с персональным эмбеддингом **выше** базовой
   (цель ≥ +1 п.п. в среднем, больше у пользователей с базой < 0.9).
2. Официальный test с `<unk>`: ≥ 91.0% (без деградации против 91.21%).
3. Обратная совместимость: старый чекпойнт грузится при `user_dim=0`; ONNX-экспорт работает.
4. Сплит чист: ни один test-пользователь не участвует в train.
5. `SPECIFICATION.md` обновлена после одобрения.

## 6. Риски и митигации

| Риск | Митигация |
|---|---|
| Переобучение эмбеддингов редких пользователей (min 4 сэмпла) | dropout на user-эмбеддинг (0.1), L2/weight-decay на таблицу эмбеддингов, при необходимости — регуляризация к `<unk>` |
| `<unk>`-эмбеддинг хуже базы на официальном test | вариант: заморозить `<unk>` = среднее обученных эмбеддингов; критерий 2 отсекает деградацию |
| Утечка пользователей между сплитами | официальный сплит уже разделён по пользователям; проверяем утверждением в P1 |
| Время обучения | те же гиперпараметры/эпохи, что у базы; запуск на CPU допустим |
| ONNX/мобильный экспорт ломается от нового входа | baked `<unk>` как константа (вход не меняется) или опциональный вход `user_idx`; решить в P4 |
| Прирост у известных < +1 п.п. | пересмотр решения: регуляризация эмбеддингов, добавление к эмбеддингу всех токенов (не только CLS), или отказ от фичи |
